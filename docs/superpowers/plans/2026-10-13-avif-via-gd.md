# Write AVIF with GD when Imagick cannot Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stop WordPress from writing empty (0 byte) `.avif` files on servers where the Imagick editor registers AVIF but cannot encode it, by making the Imagick editor decline `image/avif` so WordPress uses GD for AVIF.

**Architecture:** `hyperpress-media` adds a small `WP_Image_Editor_Imagick` subclass whose `supports_mime_type()` returns false for `image/avif`, and swaps it in through the `wp_image_editors` filter when GD can write AVIF (`imageavif()` exists). WordPress then picks GD for AVIF whenever the caller states the target type (as the `webp-uploads` plugin does), and `WP_Image_Editor::get_output_format()` falls back to the default format instead of writing an empty AVIF when only the Imagick editor was chosen.

**Tech Stack:** PHP 8.3, WordPress 6.9, PHPUnit through `docker compose run --rm php composer ...` from `plugins/`.

## Background (evidence from the owner's staging server)

- `Imagick::queryFormats( 'AVIF' )` lists AVIF (ImageMagick 6.9.12-98), `libheif-plugin-aomenc` and `libaom3` are installed, yet `Imagick::writeImage( 'x.avif' )` writes a 0 byte file with no exception. Every `.avif` under `uploads` was 0 bytes (all `-png.avif` files generated by the `webp-uploads` plugin). Browsers report "the image cannot be displayed because it contains errors".
- GD wrote a valid AVIF (4806 bytes) from the same RGBA, interlaced 120x120 PNG with `imageavif()`.
- Cause (unproven, from memory): ImageMagick 6's HEIF writer encodes HEVC only. The fix does not depend on it.
- Core facts verified in `wp-includes/media.php` and `class-wp-image-editor.php`: `_wp_image_editor_choose()` requires the editor classes before applying `wp_image_editors`, picks the first implementation whose static `test( $args )` passes (which consults `supports_mime_type( $args['mime_type'] )`), and `get_output_format()` re-checks `$this->supports_mime_type()` for the output type and otherwise uses `image_editor_default_mime_type`.

## Global Constraints

- Plugin `hyperpress-media`, namespace `HyperPress\Media`, one class per concern in `src/`, text domain `hyperpress`, class guard `defined( 'ABSPATH' ) || exit;` (these classes need WordPress). Do not change plugin headers, `Convention` or the other plugins. No change to the theme.
- The replacement is applied only when the filter `hyperpress_media_avif_via_gd`, which defaults to `function_exists( 'imageavif' )`, is true (owners can force it false, tests can force it true); everything other than `image/avif` behaves exactly as `WP_Image_Editor_Imagick` does.
- The Imagick subclass must be defined lazily (the parent class is only guaranteed to be loaded once `_wp_image_editor_choose()` runs), i.e. its file is required from inside the `wp_image_editors` callback after `require_once ABSPATH . WPINC . '/class-wp-image-editor.php'` and `'/class-wp-image-editor-imagick.php'`; it must not be loaded at plugin boot.
- Tooling runs in Docker only, from `plugins/`: `docker compose run --rm php composer lint|test:unit|test:integration` (append `-- --filter <Name>`); the theme tests from `themes/hyperpress-foundation/` too (they load every plugin). Lint stays at 0; check its exit code explicitly. Never read `.env*` files.
- Commit with explicit paths: `git add <paths>` then `git commit -m "..." -- <paths>`. Tick this plan's boxes in the same commit as the code.

## Review Focus

- Imagick available but unable to write AVIF, GD able: `_wp_image_editor_choose( array( 'mime_type' => 'image/avif' ) )` returns `WP_Image_Editor_GD`; for JPEG, PNG and WebP it still returns the Imagick editor class (the subclass).
- Only the Imagick editor present, or `imageavif()` missing: nothing is replaced, behaviour unchanged.
- The Imagick subclass picked from a PNG source and saved with `image/avif` does not write an empty `.avif`: `get_output_format()` falls back to the default format.
- Opt-out filter returns false: the original class list is returned untouched.
- The replacement keeps the order of the implementations list and does not duplicate entries.

## File Structure

- `plugins/hyperpress-media/src/ImageEditor/AvifViaGd.php`: registers the filter and swaps the class (`register()`, `editors( array ): array`).
- `plugins/hyperpress-media/src/ImageEditor/ImagickWithoutAvif.php`: the subclass (loaded lazily).
- `plugins/hyperpress-media/src/Plugin.php`: `boot()` calls `ImageEditor\AvifViaGd::register()`.
